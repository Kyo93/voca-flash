# Proposal: Character Evolution With EXP
Generated by: cm-brainstorm-idea
Date: 2026-04-25

## Why we're doing this
The current character MVP lets users unlock and display characters with available EXP. Evolution adds a longer-term motivation loop: after unlocking a character, learners can keep investing EXP into that character to transform its form, visual presence, and status.

## Important IP Boundary
Use the "Goku / Pokemon" idea only as a mechanic reference: staged transformation, stronger visual form, collection pride. Do not use names, likenesses, silhouettes, sounds, or assets from those franchises. VocaFlash should use original scholar/fantasy/learning-themed characters.

## Qualified Problem
For learners who already unlocked a character, the collection can become static. They need a reason to keep earning EXP after unlocks. The feature should create a long-term progression loop without breaking level progression or making the economy confusing.

### Root Causes
1. Current character state is binary: locked or unlocked.
2. EXP spending currently has one destination: unlock a character.
3. Dashboard display has no visible "growth over time" for selected characters.

### Impact if not addressed
- Character collection may feel finished too early.
- High-EXP users need a deeper sink than unlock-only costs.
- Dashboard personalization remains shallow.

## Options Evaluated
### Option A: Automatic Evolution by Lifetime EXP
Characters evolve automatically when the user's lifetime `totalXp` reaches thresholds.

**Effort:** S  
**Risk:** Low  
**Pros:** No extra spending logic, easy to explain, no risk of buyer regret.  
**Cons:** User does not actively choose which character grows; weak emotional ownership.

### Option B: Spend Available EXP to Evolve Selected Characters
Each character has stage costs. User spends `availableXp` to evolve a specific unlocked character. Lifetime `totalXp` never decreases; `spentXp` increases.

**Effort:** M  
**Risk:** Medium  
**Pros:** Strong agency, matches the user's request, reuses wallet model, creates long-term EXP sink.  
**Cons:** Needs careful UI to explain "available EXP" vs "total EXP"; needs idempotent transaction safety.

### Option C: Character Affinity EXP
Characters gain their own affinity EXP when displayed during Study/Arena. Evolution uses affinity, not global available EXP.

**Effort:** L  
**Risk:** Medium/High  
**Pros:** Very thematic; encourages choosing a companion before studying.  
**Cons:** Adds another currency-like system and more event wiring; too much for current MVP.

## Recommendation
Choose **Option B: Spend Available EXP to Evolve Selected Characters**.

### Why Option B
1. It directly satisfies "EXP dùng để tiến hóa".
2. It fits the existing wallet architecture: `availableXp = totalXp - spentXp`.
3. It gives learners meaningful choice: unlock a new character or evolve a favorite.
4. It is easier to ship than affinity EXP but deeper than automatic thresholds.

### Why not the others
- **Option A:** too passive; feels like another badge threshold.
- **Option C:** interesting later, but adds a second progression currency before the first character economy is proven.

## Product Model
### Evolution Track
Each character has 3-4 original stages:
- Stage 1: Base form, unlocked with character.
- Stage 2: Trained form.
- Stage 3: Master form.
- Stage 4: Legendary form for rare/epic characters only.

Example original naming pattern:
- `seedling_scholar`: Mầm học giả -> Học giả non trẻ -> Người dẫn đường tri thức
- `arena_guardian`: Vệ binh Arena -> Đội trưởng Arena -> Hộ pháp ký ức
- `lexical_sage`: Hiền giả từ vựng -> Đại hiền giả -> Tinh tú từ vựng

### Economy
- Unlock cost and evolution cost are separate catalog fields.
- Evolving spends available EXP and increments global `spent_xp`.
- Lifetime level and badges continue to use `totalXp`, so they never regress.
- Evolution should be idempotent: buying an already-owned stage must not double-spend.

### UX
- Character grid shows current stage badge and next evolution cost.
- Selected Dashboard character shows its current form and a small evolution progress strip.
- On character detail/card:
  - If locked: show unlock CTA.
  - If unlocked and next stage affordable: show evolve CTA.
  - If unlocked but not affordable: show remaining EXP.
  - If max stage: show maxed state.

## Technical Direction
### Data Shape
Extend catalog:
- `evolutionStages: Array<{ stage, costXp, nameKey, descriptionKey, icon?, swatchClass? }>`

Extend storage:
- `user_character_unlocks.current_stage INTEGER NOT NULL DEFAULT 1`
- `user_character_unlocks.evolution_spent_xp INTEGER NOT NULL DEFAULT 0`
- optional `evolved_at TIMESTAMPTZ`

Add RPC:
- `evolve_user_character(p_user_id, p_character_id, p_target_stage, p_cost_xp)`
  - Verify ownership/admin.
  - Lock reward row and unlock row.
  - Verify character is unlocked.
  - Verify target stage is exactly current stage + 1.
  - Verify available EXP is enough.
  - Increment `user_reward_progress.spent_xp`.
  - Update `current_stage` and `evolution_spent_xp`.
  - Return reward progress + character states.

## Open Design Question
Should every character have the same number of evolution stages, or should rarity control max stages?

Recommendation: rarity controls max stages. Starter/common get 3 stages; rare/epic get 4 stages. This makes higher rarity characters feel special without requiring more catalog entries for every character.
